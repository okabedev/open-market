# 설계 정합성 점검

결과는 "문제 / 근거(파일:줄) / 고칠 방법" 표로 보고한다. 고치기 전에 사용자에게 보여준다.
읽기만으로 끝내지 않는다. 아래 이름들은 저장소 전체를 grep해서 모든 언급 위치를 대조한다.

## 1. 이름
- [ ] 서비스 이름과 포트, 스키마가 overview, CLAUDE.md, `settings.gradle.kts`, config-repo, compose, gateway 라우트에서 같은가
- [ ] 이벤트 이름과 토픽이 context-map, messaging, 코드(도메인 이벤트, 리스너), `infra/kafka/topics`에서 같은가
- [ ] 상태 값과 용어가 glossary와 코드 enum에서 같은가
- [ ] `-service` 접미사나 괄호 부가 설명이 붙은 서비스 이름이 없는가

## 2. 규칙
- [ ] ArchUnit 규칙이 conventions.md 의존 방향 표와 같은가
- [ ] 서비스 사이 상태 변경이 동기 호출로 구현된 곳이 없는가
- [ ] 리스너가 모두 멱등 처리를 거치는가. 배치가 다시 실행해도 결과가 같은가
- [ ] 중복되면 안 되는 상태 변경 API가 `Idempotency-Key`를 받는가
- [ ] 이벤트 페이로드나 로그에 비밀 값, 불필요한 개인정보가 없는가
- [ ] 발행 이벤트마다 JSON 예시와 소비자 역직렬화 테스트가 있는가

## 3. 문서
- [ ] "M<n>에서 확정"으로 남은 항목 중 이미 정해진 것이 있는가
- [ ] 같은 정보가 두 곳에 복사되어 서로 다르지 않은가(원본 문서 한 곳 + 링크)
- [ ] 상대 링크가 모두 실제 파일을 가리키는가
- [ ] roadmap 체크 상태, risks 상태가 실제와 맞는가
- [ ] ADR과 다른 구현이 있다면 새 ADR이 있는가
- [ ] 루트 CLAUDE.md가 150줄 이내이고 바꾸지 않는 결정이 빠짐없이 있는가

## 4. 실행
- [ ] 빌드, 테스트, 포매터, ArchUnit이 통과하는가
- [ ] dev-setup.md대로 새로 시작해도 스택이 뜨는가(마일스톤 마감 때)
