# 로드맵

일정은 기한 없는 **범위 단위 마일스톤**으로 관리한다. 완료 기준을 채우면 바로 닫고 다음으로 넘어간다.
진행 절차는 `.claude/skills/milestone`에 있다.

## 마일스톤을 닫는 조건
1. 아래 "완료 기준 E2E"가 통과한다.
2. CI가 녹색이다.
3. `design-review` 점검 결과의 문제를 고쳤다.
4. 사용자가 확인하면 `m<n>` 태그를 단다.

### M0 회고
- 완료 기준 E2E(2026-10-18): 빈 볼륨으로 기본·`obs`·`apps` profile을 띄웠다. gateway 경유 `POST /api/member/v1/ping`은 202였다. 이벤트가 outbox → Debezium → `member.ping` → `PingSentListener`로 갔다. 같은 메시지(키·값·헤더)를 다시 넣어도 처리 로그와 `processed_event`는 1건, DLT는 0건이었다. Tempo에서 trace 하나에 gateway → member HTTP → Kafka 소비 스팬이 이어졌고, Loki에서 같은 trace id로 로그 2줄이 나왔다.
- 잘된 점: 리스크(R1~R6)를 기능보다 먼저 실측으로 확인했다. 기본 설정의 함정을 찾아 고쳤다. Kafka 재접속 뒤 5분간 발행이 멈췄고, Redis가 응답하지 않으면 요청이 60초 멈췄고, JVM이 힙 상한을 5GB로 잡았다. 버전과 도구 선택은 ADR에 근거를 남겼다. E2E는 별도 Compose 프로젝트(`-p`)로 사용자 볼륨과 섞지 않고 반복할 수 있다.
- 바꿀 점: ESLint 10, TypeScript 7을 올렸다가 되돌렸다. 최신 버전은 피어 지원을 먼저 확인한다. 마일스톤 E2E가 수동 명령의 나열이다. 권한이 필요한 작업(GitHub 설정 적용)은 계획 단계에서 사용자가 실행할 몫으로 나눈다.
- M1에 넘기는 것: 샘플 API·토픽 제거(M1 항목), 프론트 미정 항목([clients/CLAUDE.md](../clients/CLAUDE.md)), R7·R8 확인, 마일스톤 E2E 스크립트화. 메모리 재측정(R6)은 M3, 복제 슬롯 무효 시나리오(R5)는 M6에서 한다.

### M1 회고
- 완료 기준 E2E(2026-10-19): `infra/e2e/run.sh m1`로 빈 볼륨의 별도 Compose 프로젝트(기본·`apps`)와 앱 3개를 띄웠다. 시나리오 2개가 통과했다(19.6초, 스택 기동 포함 273초). 가입 → 인증 메일 → 로그인 → 입점 신청 → 승인 전 판매자 API 403 → 관리자 승인 → 토큰 갱신 후 판매자 API 200 → 판매자 센터 진입. 프로필·배송지·탈퇴 흐름도 함께 돌았다. 끝난 뒤 컨테이너·볼륨·앱 프로세스가 남지 않았다.
- 잘된 점: R7·R8을 기능보다 먼저 확인하고 ADR(0013, 0014)로 남겼다. PR마다 Compose와 실제 브라우저로 확인해서 단위 테스트로는 안 잡히는 문제를 찾았다. 엄격한 레이트 리밋과 기본 리밋의 Redis 키 충돌, BFF 주소 하나로 묶이던 가입 한도, 로그인 화면의 CSRF 입력 중복, 리스너 둘이 한 그룹일 때 첫 레코드를 놓치던 테스트 설정, 탈퇴 계정이 남은 auth 세션으로 인가 코드를 받던 문제와 탈퇴 뒤 로그아웃 400이다. 사용자가 정할 일(마스킹 범위, 판매자 탈퇴, 재가입, UI 스택, E2E 범위)은 선택지를 들고 물었고 문서에 남겼다. 마일스톤 E2E가 스크립트 한 줄이 됐다.
- 바꿀 점: `main` push CI가 두 번 실패했는데(gateway 테스트가 느린 러너에서 Redis 첫 연결 200ms를 넘겨 health DOWN) 마감 때 발견했다. PR을 merge한 뒤 `main` 실행 결과도 확인한다. 탈퇴(PR #28)에서 로그아웃·재로그인 흐름을 보지 않아 다음 PR에서 고쳤다. 인증 상태를 바꾸는 기능은 브라우저 흐름까지 확인한다. 새 상태 값은 용어집의 철자 관례와 먼저 대조한다(`CANCELED` → `CANCELLED`로 고쳤다).
- M2에 넘기는 것: 판매자 정지 시 상품 판매 중지(catalog가 `SellerSuspended` 소비), 토큰 없이 여는 서비스 경로 설정(`common-security`, 상품 조회), 상품 등록 같은 큰 폼에서 즉시 검증 재검토(ADR 0015). 승인·반려 알림 메일은 M4, 판매자 탈퇴·정리는 M5, 탈퇴의 진행 중 주문 확인은 M3에서 order에 연결한다. gateway health가 Redis 첫 연결 지연으로 잠깐 DOWN일 수 있는 점은 M6 운영 점검에서 health 그룹과 함께 정리한다.

### M2 회고
- 완료 기준 E2E(2026-10-20): `infra/e2e/run.sh m2`로 빈 볼륨의 별도 Compose 프로젝트(기본·`apps`, Elasticsearch 포함)와 앱 3개를 띄웠다. 시나리오 2개가 통과했다(38.8초).
  - `m2-product-search`: 판매자가 이미지와 옵션 조합으로 등록하면 판매 시작 뒤 15초 제한 안에 구매자 검색에 나오고, 판매를 중지하면 빠진다. Compose 확인에서는 catalog outbox → search 반영이 5초 안이었다.
  - `m2-product-management`: 재고로 품절되면 검색 뒤로 가고, 수정이 반영되고, 관리자가 제재하면 구매자에게 404가 된다.
  - 회귀 확인으로 `m1`도 다시 통과했다.
- 잘된 점
  - R10(nori)을 기능보다 먼저 이미지로 만들고, 분석기 조합 셋을 상품명으로 비교해 ADR 0016으로 남겼다.
  - 두 토픽(상품, 재고)의 순서가 섞이는 문제를 코드 전에 context-map에서 정했다(판매 가능 리비전). 그래서 재고 조정이 상품 행을 잠그지 않는다.
  - PR마다 실제 스택과 브라우저로 확인해 단위 테스트로는 안 잡히는 문제를 찾았다.
    - file 컨테이너가 512m에서 스왑을 썼다(768m, 힙 40%)
    - catalog OpenAPI에서 중첩 `Sku` 넷이 한 스키마로 합쳐져 생성 타입이 틀렸다
    - 서버 페이지가 클라이언트 모듈 함수를 불러 500이 났다
    - 행마다 있는 사유 폼의 이름표가 첫 행 입력을 가리켰다(M1 화면에도 있던 접근성 버그)
  - 사용자가 정할 일(카테고리 관리 방식, 상품 폼에 react-hook-form 도입 여부)은 선택지를 들고 물었고 문서에 남겼다. PR은 11개(#32~#42)로 나눠 하나씩 merge했다.
- 바꿀 점
  - 로컬에 브라우저 시스템 라이브러리가 없다는 것을 판매자 화면 PR에서야 알았다. dev-setup의 설치 명령(`sudo corepack …`)은 M1부터 동작하지 않았다. 마일스톤을 시작할 때 `run.sh`로 이전 마일스톤 E2E를 한 번 돌려 환경을 확인한다.
  - 검색 `totalCount`가 문서(1만 건 상한)와 달리 매번 정확히 셌다. design-review에서야 찾았다. API 동작을 문서에 적을 때는 그 동작을 테스트로 고정한다.
  - 화면 PR마다 커밋하지 않는 임시 시나리오를 다시 썼다. 다음에는 첫 화면 PR부터 마일스톤 E2E 파일을 조금씩 늘린다.
- M3에 넘기는 것
  - 재고 예약·확정·해제와 동시성(CAT-4). 예약·해제도 판매 가능 여부 계산(`ProductAvailabilityCalculator`)을 거쳐 `StockAvailabilityChanged`를 낸다.
  - 메모리 전체 재측정(R6)
  - `packages/bff`의 Redis Testcontainers 테스트가 가끔 실패한다("Unknown RESP type 72"). 다시 돌리면 통과한다.
  - 나중 마일스톤으로 미룬 것
    - M5: 별점·판매량 필터·정렬, 자동완성, 동의어·사용자 사전
    - M6: 판매자 한 명의 상품이 아주 많을 때 정지·해제를 나눠 처리

### M3 회고
- 완료 기준 E2E(2026-10-21): `infra/e2e/run.sh m3`로 빈 볼륨의 별도 Compose 프로젝트(기본·`apps`·`e2e`, 가짜 PG)와 앱 3개를 띄웠다. 시나리오 4개가 두 번 연속 통과했다(각 2.6분).
  - `m3-order-payment`: 장바구니 주문 → 결제 인증 취소 → 다시 결제 → 결제 완료, 구매자 주문 내역·상세, 판매자 하위 주문, 결제 전 구매자 취소
  - `m3-order-saga`: 판매자 둘의 상품을 한 번에 주문·결제(하위 주문 둘), 마지막 한 개를 두 주문이 동시에 가져갈 때 재고 부족 취소, 결제하지 않은 주문의 만료와 예약 해제, 결제 기한 직전 승인의 응답이 만료 뒤에 올 때 토스(가짜 PG) 전액 자동 취소
- 잘된 점
  - R9를 기능보다 먼저 확인해 ADR 0018로 정했다(문서용 공개 키, 서버 승인, 웹훅 대신 조회, E2E는 가짜 PG). 그래서 만료와 승인의 경합을 E2E에서 매번 같은 순서로 재현했다.
  - 실제 토스 테스트 환경으로 승인과 보상 취소(전액 취소)를 PR마다 손으로 확인했다. 퀵계좌이체 흐름은 브라우저 자동화로 승인까지 갔다.
  - M2 회고대로 첫 화면 PR부터 마일스톤 E2E 파일을 늘렸다. 마감 E2E에서 결제 준비 경합을 찾아 결제 조회 API와 화면 대기로 고쳤다(#59).
  - 사용자가 정할 일(결제 준비 경합의 고치는 방법, 메모리 상한)은 선택지를 들고 물었다. PR은 18개(#43~#60)로 나눠 하나씩 merge했다.
- 바꿀 점
  - E2E가 한 IP에서 계정 여러 개를 만들고 로그인해 가입·인증 한도와 로그인 한도에 차례로 걸렸다. 그래서 세 번을 다시 돌렸다. 공유 한도가 있는 흐름은 시나리오를 쓰기 전에 한도부터 본다.
  - 다른 서비스가 이벤트로 만드는 데이터(주문 결제 대기 → payment의 결제)를 화면이 바로 쓰면 경합이 생긴다. 이벤트 사이에 있는 화면은 설계할 때 상대 서비스의 준비 상태를 확인한다.
  - 메모리가 512m 상한에 거의 닿은 것을 마감 재측정에서야 알았다. 서비스나 큰 라이브러리를 더할 때마다 컨테이너 메모리를 본다.
- M4에 넘기는 것
  - 토스가 취소를 거절한 결제(`cancel_failure_code`)의 운영자 처리. 환불 실패(`RefundFailed`)의 관리자 재시도와 함께 정한다.
  - 배송비 규칙(반품 배송비 차감과 함께), "바로 구매"
  - `packages/bff`의 Redis Testcontainers 테스트가 가끔 실패한다("Unknown RESP type 72"). M2에서 넘어왔다.
  - 메모리 재측정은 서비스가 15개가 되는 M5 마감 전에 한다(R6).

### M4 회고
- 완료 기준 E2E(2026-10-22): `infra/e2e/run.sh m4`로 빈 볼륨의 별도 Compose 프로젝트(기본·`apps`·`e2e`, 가짜 PG)와 앱 3개를 띄웠다. 시나리오 4개가 통과했다(3.8분).
  - `m4-completion`(완료 기준): 판매자 둘의 상품을 한 주문으로 결제 → 둘 다 발송·배송 완료 → 한쪽 단순 변심 반품 → 판매자 재입고 승인 → 반품 배송비를 뺀 19,000원 부분 환불(가짜 PG `PARTIAL_CANCELED`, 남은 14,000원) → 재입고. 다른 하위 주문은 손대지 않아 배송 완료 30초(7일 대신) 뒤 자동 구매확정
  - `m4-seller-fulfillment`: 할 일 탭, 발주 확인·발송(송장 형식), 반품 승인(사진, 재입고 필수), 교환 거부 뒤 다시 신청받아 승인과 교환 재발송
  - `m4-buyer-fulfillment`: 바로 구매(장바구니 유지), 발송 전 취소와 환불, 구매확정, 교환 사유 제한, 판매자 거부 뒤 중재 요청
  - `m4-admin-fulfillment`: 세 앱의 인앱 알림과 이동, 관리자 교환 중재 승인(사진), 가짜 PG가 거절한 환불을 관리자가 다시 시도
- 잘된 점
  - 상태·환불 금액·이벤트 필드를 설계 PR에서 먼저 정했다(fulfillment.md, context-map). 이후 PR 15개가 설계를 거의 바꾸지 않았다.
  - 사용자가 정할 일(반품 배송비, 인앱 알림 방식, 관리자 알림 대상)은 선택지를 들고 물었다. 마감 때 ADR 0019로 남겼다.
  - M3 회고대로 첫 화면 PR부터 마일스톤 시나리오를 늘렸다. 시나리오가 PR의 단위 테스트로는 안 잡히는 버그를 찾았다(모두 읽음 뒤 머리글의 안 읽은 수가 그대로였다).
  - 실제 토스 테스트 환경에서 부분취소를 끝까지 확인했다(퀵계좌이체 승인 → 반품 → 4,000원 부분 환불, `PARTIALLY_CANCELLED`). 환불 거절은 가짜 PG의 취소 거절 설정으로 E2E에서 재현했다.
  - PR은 17개(#61~#77)로 나눠 하나씩 merge했다.
- 바꿀 점
  - merge 뒤 `main` CI를 보지 않아 `main`이 두 번 빨갛게 끝난 것(payment·auth의 간헐 실패)을 PR 15에서야 알았다. M1 회고에 적은 교훈을 지키지 못했다. merge하면 `main` 실행이 끝날 때까지 본다.
  - bff Redis 테스트의 간헐 실패는 원인을 재현하지 못하고 방어적으로만 고쳤다. 다시 나면 그때의 로그와 포트를 남긴다.
  - 긴 E2E 뒤 개발 스택을 다시 띄울 때 오래 전에 만든 `kafka-init`, `connect` 컨테이너의 bind mount가 비어 보여 exit 127로 실패했다. 컨테이너를 다시 만들어(`--force-recreate`) 풀었다. 원인은 확인하지 못했다.
- M5에 넘기는 것
  - notification이 메모리 상한에 가장 가깝다(peak 564MB/640MB). 리뷰·정산 알림을 더하면 다시 본다. 서비스 15개 재측정은 M5 마감 전에 한다(R6).
  - 판매자 클레임 알림은 클레임 ID만 있어 클레임 진행 중 목록으로 간다. 하위 주문 상세로 바로 가려면 알림 대상에 하위 주문 ID를 더한다.
  - 여러 서비스 테스트가 Awaitility `untilAsserted` 안에서 JdbcClient `single()`을 쓴다. 단언 실패가 아닌 예외는 다시 시도되지 않는다. 간헐 실패가 나면 같은 방법(목록으로 읽어 단언)으로 고친다.
  - 실시간성이 필요한 알림이 생기면 SSE를 다시 검토한다(ADR 0019).

### M5 회고
- 완료 기준 E2E(2026-10-26): `infra/e2e/run.sh m5`로 빈 볼륨의 별도 Compose 프로젝트(서비스 15개, 가짜 PG)와 앱 3개를 띄웠다. 시나리오 3개가 통과했다(4.2분). 마감 전에 `m1`~`m5`를 모두 다시 돌려 15개가 통과했다.
  - `m5-completion`(완료 기준): 판매자 선착순 쿠폰 4,000원을 받아 40,000원 주문에 적용(36,000원 결제) → 발송·자동 구매확정 → 별점 4점 리뷰가 검색 결과에 `4.0 (리뷰 1개)` → 정산 예정 32,000원 → 정산 작업으로 확정, 한 번 더 돌려도 정산 하나·32,000원 → 관리자가 정산 계좌를 보고 지급 → 판매자 지급 완료와 정산 확정·지급 알림. E2E 정산 기간 1분, 마감 지연 5초
  - `m5-buyer-coupon`: 판매자·플랫폼 쿠폰을 화면에서 만들고 받아 주문서에 둘 다 적용(24,300원), 사용함, 발급 수, 발급 중지 뒤 상품 상세에서 빠짐
  - `m5-buyer-search`: 사진 리뷰 작성, 별점순·판매량순·별점 필터·자동완성, 새 리뷰 알림에서 판매자 답글, 관리자 숨김·다시 보임, 카테고리 수수료율이 정산 예정 내역에 쓰임, 정산 작업 즉시 실행
- 서비스 15개 메모리(R6): 시나리오 뒤 상한 도달·OOM 없음, VM 12.8GB/20GB. 상한은 그대로다(risks.md "M5 재측정").
- 잘된 점
  - 위험한 두 곳(선착순 발급 R11, 예약 합류 R12)을 설계 다음 PR에서 동시성 테스트로 먼저 확인했다. 이후 PR이 그 규칙을 바꾸지 않았다.
  - 화면 PR을 앱과 기능 단위로 나눴다(shop 13a~13d, seller 14a~14c, admin 15a~15d). PR마다 `m5-*` 시나리오를 늘려 완료 기준 시나리오는 처음 실행에서 통과했다.
  - 두 앱 이상이 쓰는 것은 그때그때 `packages/ui`로 옮겼다(쿠폰 문구·폼·검사, 별점, 정산 금액·내역·기간 문구).
  - M4 회고대로 merge할 때마다 `main` CI가 끝날 때까지 봤다. M5 기능 PR(#78~#101)의 `main` 실행은 모두 성공했다. 마감 PR(#102)의 `main` 실행은 order 통합 테스트의 Testcontainers 컨테이너가 시작 시간 안에 뜨지 않아 한 번 실패했고, 실패한 작업을 다시 돌려 통과했다.
  - M4에서 원인을 모르던 bind mount 문제의 원인을 찾았다. 지운 워크트리 경로에서 만든 컨테이너가 그 경로를 마운트하고 있었다. 개발용 스택은 메인 checkout(`--project-directory`)에서만 띄운다.
  - PR은 24개(#78~#101)로 나눠 하나씩 merge했다.
- 바꿀 점
  - 화면 PR을 시작하고서야 필요한 조회 API가 없는 것을 알았다. 관리자가 판매자 정산 계좌를 읽는 API(15d에서 member에 더함), 쓸 수 있는 리뷰 한 건 조회(주문 상세로 대신함)가 그랬다. 설계 PR에서 화면마다 읽을 API를 대조한다.
  - 이전 마일스톤 시나리오의 기대값 결함(M3 배지 문구, M4 알림 이동)을 다른 PR(13c)에서야 찾았다. 화면이나 알림 이동을 바꾸면 그 화면을 쓰는 마일스톤 E2E를 같은 PR에서 돌린다.
  - R11·R12의 결정을 확인한 PR에서 ADR로 남기지 않고 마감 점검에서 썼다(ADR 0020, 0021). 리스크를 확인한 PR에서 ADR까지 쓴다.
  - 로컬 `pnpm format:check`가 E2E 보고서 때문에 실패하는 것을 PR마다 넘겼다. 마감 점검에서 `.prettierignore`에 더했다.
  - CI의 Testcontainers 시작 시간 초과(여러 모듈이 동시에 컨테이너를 띄울 때)는 원인을 재현하지 못했다. 다시 나면 그때의 로그를 남기고 시작 시간 제한이나 동시 실행 수를 본다.
- M6에 넘기는 것
  - 판매자 주문 조회에는 쿠폰 할인 필드가 없다. 판매자 새 주문 알림과 화면은 할인 전 상품 금액이다(notification.md "M5에서 더한 것").
  - promotion·settlement는 상호를 갖지 않아 관리자 쿠폰·정산 목록이 판매자 ID로 보인다. 상호가 필요하면 member에 여러 판매자를 한 번에 읽는 조회를 더한다.
  - 장애 주입(M6)에서 쿠폰 예약 실패 조합과 Redis 장애 중 발급을 서비스를 모두 띄운 상태로 본다(ADR 0020, 0021에서 확인하지 않은 것).
  - 부하 중 메모리 측정(k6)과 서비스당 연결 풀(5) 조정, 검색 관련도의 판매량 가중치 재검토, 관리자 감사 로그 조회(ADM-5).

- 범위 결정(2026-10-20)
  - 쿠폰은 M5다. M3 주문은 쿠폰 없이 재고 예약 결과만 기다리고, `OrderPlaced`의 발급 쿠폰 ID 목록은 비어 있다.
  - ORD-4는 조회만 한다. 하위 주문 처리(발주 확인, 발송)는 M4 fulfillment에서 한다.
  - 결제 만료 시간(15분)은 설정으로 두고, E2E에서만 짧게 준다.
  - 주문(2026-10-20): 배송지는 주문 요청 본문으로 받는다(order는 member를 부르지 않는다). 가격 변경은 요청의 기대 가격과 비교한다. 장바구니는 결제가 끝나면(`PAID`) 주문한 SKU를 뺀다. M3 주문은 무료 배송이고, 배송비 규칙은 M4에서 정한다.
  - 실제 토스 연동은 토스 문서용 공개 테스트 키로 R9와 PR마다 손으로 확인한다(주문서형 연동 키는 사업자 정보가 있어야 발급된다). 완료 기준 E2E는 토스 API와 SDK를 흉내 내는 가짜 PG로 돌린다. 승인 응답을 늦춰 만료와 승인의 경합을 매번 재현하기 위해서다([ADR 0018](adr/0018-toss-payments-integration.md)).
- 순서: R9 → order 골격·장바구니·SKU 조회·서킷 브레이커 → 재고 예약 → 주문 생성 → 만료·취소 → payment 승인 → order 결제 반영 → 보상 취소 → 화면(장바구니 → 주문서·결제 → 가짜 PG → 주문 목록·상세) → E2E·R6

**완료 기준 E2E**: 판매자 둘의 상품을 한 번에 주문하고 토스 테스트 결제로 승인하면, 주문이 `PAID`가 되고 하위 주문 둘이 생긴다. 재고 부족 주문은 취소되고 예약이 풀린다. 결제하지 않은 주문은 만료된다. 만료 직후 승인된 결제는 자동 취소된다.

  - 쿠폰은 결제 전 취소일 때만 복원한다. 결제 후 클레임은 하위 주문에 나눈 할인을 뺀 결제 금액을 환불한다.
  - 리뷰는 고치거나 지우지 않는다. 작성 기한은 없다. 답글은 리뷰마다 하나이고 고칠 수 있다.
  - 검색 판매량은 구매확정 수량이다. 자동완성은 완성된 글자 단위이고 자모·초성 검색은 하지 않는다.
  - 정산 배치는 `@Scheduled` + ShedLock이다(Spring Batch 안 씀). 정산 기간 길이는 설정이고 E2E는 줄인다. 확정한 정산은 다시 계산하지 않는다.
  - 판매자 탈퇴(폐점)는 그대로 막는다.
- 순서: 설계 → promotion 골격·정책 → 선착순 발급(R11) → 쿠폰 예약 → order 쿠폰 적용(R12) → review 골격·작성 → 답글·숨김 → settlement 골격(R6 중간 측정) → 정산 배치·지급 → search v2·별점·판매량 → 자동완성 → 알림 → 화면(shop → seller → admin, 첫 화면 PR부터 `m5-*` 시나리오를 늘린다) → E2E

**완료 기준 E2E**: 선착순 쿠폰을 받아 주문에 적용하고, 구매확정 후 리뷰를 쓰면 검색 결과의 별점이 바뀐다. 정산 배치를 두 번 돌려도 정산 금액이 같다.

- 범위 결정(2026-10-26)
  - DLT 메시지는 소비한 서비스가 자기 스키마에 모으고, 다시 보낼 때는 실패한 그룹만 처리하게 헤더로 표시한다. 새 서비스는 만들지 않는다(ADR 0022).
  - 감사 로그와 DLT 메시지 화면은 admin BFF가 서비스마다 물어 시간순으로 합친다. 운영 지표는 Prometheus가 아니라 order·payment의 업무 DB에서 센다(ADR 0023).
  - 관리자 TOTP는 `ADMIN` 역할 계정이면 어느 클라이언트로 로그인하든 필수다. 첫 로그인에 등록하고 복구 코드를 준다.
  - 장애 주입 도구: DB 지연은 Toxiproxy(`fault` profile), PG 지연은 가짜 PG다. 버전은 장애 주입 PR에서 정한다.
  - M5에서 넘긴 것 중 판매자 주문의 쿠폰 할인 필드와 관리자 쿠폰·정산 목록의 상호 표시는 M6 범위(운영 성숙도) 밖이라 하지 않는다. M6 이후 백로그다.
- 화면별 API(M5 회고: 설계에서 화면이 읽을 API를 대조한다)

  | 화면 | 읽고 쓰는 API | 있는지 |
  |---|---|---|
  | admin 운영 지표 | order `GET /v1/admin/metrics/orders`, payment `GET /v1/admin/metrics/payments` | 새로 만든다 |
  | admin 감사 로그 | 서비스마다 `GET /v1/admin/audit-logs` | 새로 만든다(`common-web`) |
  | admin DLT 메시지 | 서비스마다 `GET /v1/admin/dead-letters`, `POST .../{id}/retry`, `POST .../{id}/discard` | 새로 만든다(`common-messaging`) |
  | auth TOTP 등록·확인 | auth 화면(Thymeleaf), gateway 밖 | 새로 만든다 |
- 순서: 설계 → k6 첫 측정(R13) → 성능 개선 → 장애 주입(R16) → DLT 재처리(R14) → 감사 로그 조회 → 운영 지표 → admin 화면 → TOTP(R15) → 대시보드·알림 → 보안 점검 → 런북 → E2E

**완료 기준 E2E**: k6 시나리오에서 NFR-9 목표를 만족한다. Kafka를 1분간 중지했다가 다시 띄워도 이벤트 유실이 없고, Saga가 끝까지 진행된다.
