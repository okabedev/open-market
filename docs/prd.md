# 제품 요구사항 (PRD)

## 1. 목적
여러 판매자가 입점해 상품을 팔고, 구매자는 여러 판매자의 상품을 한 번에 주문하는 **오픈 마켓**을 만든다.
목표는 데모가 아니라 **실제로 운영할 수 있는 수준**이다. 그래서 정합성, 장애 대응, 관측성 같은 비기능 요구사항도 기능 요구사항만큼 중요하게 다룬다.

제약: 비용 0. 모든 구성 요소는 Docker Compose로 로컬에서 실행한다. 외부 연동은 무료 테스트 환경(토스페이먼츠 테스트 키)만 쓴다.

## 2. 사용자 유형
| 유형 | 설명 | 앱 |
|---|---|---|
| 구매자 (Buyer) | 상품을 검색, 주문, 결제하고 배송과 클레임을 관리한다 | `clients/apps/shop` |
| 판매자 (Seller) | 입점 심사를 거쳐 상품, 재고, 주문, 배송, 클레임, 정산을 관리한다 | `clients/apps/seller` |
| 관리자 (Admin) | 입점 심사, 상품 제재, 쿠폰, 정산 지급, 운영 지표를 관리한다 | `clients/apps/admin` |

판매자 계정은 구매자 계정에 판매자 역할을 더한 것이다. 한 계정이 구매자이면서 판매자일 수 있다. 관리자 계정은 가입으로 만들 수 없고 운영자가 시드로 만든다.

## 3. 기능 요구사항
각 항목은 `ID — 유저스토리`와 수용 기준(AC)으로 적는다. 담당 서비스는 절 제목 괄호에 적는다.

### 3.1 계정·회원 (auth, member)
- **ACC-1 — 구매자는 이메일로 가입하고 로그인한다.**
  - AC: 이메일 인증을 마쳐야 주문할 수 있다. 비밀번호는 10자 이상이고 영문과 숫자를 포함해야 한다.
  - AC: 로그인은 OAuth2 Authorization Code + PKCE로 한다. 브라우저는 토큰을 보지 못한다(BFF).
  - AC: 로그인에 5회 연속 실패하면 계정을 15분 잠근다.
- **ACC-2 — 구매자는 소셜 계정으로 로그인한다.** (선택 범위. M1에서 제외했다(2026-10-18). 외부 IdP 앱 등록이 필요해 로컬·비용 0 원칙과 맞지 않는다. M6 이후 백로그)
- **ACC-3 — 구매자는 회원 정보와 배송지를 관리한다.** 배송지는 최대 10개, 기본 배송지는 1개다.
- **ACC-4 — 구매자는 탈퇴한다.**
  - AC: 진행 중인 주문이나 클레임이 있으면 탈퇴할 수 없다. (order가 생기는 M3에서 연결한다. M1은 조회 포트만 두고 항상 "없음"으로 답한다)
  - AC: 탈퇴하면 개인정보를 바로 가명 처리하고, 법정 보관 대상인 거래 기록만 남긴다.

### 3.2 판매자 입점 (member)
- **SEL-1 — 회원은 사업자 정보와 정산 계좌를 입력해 입점을 신청한다.**
- **SEL-2 — 관리자는 입점 신청을 승인하거나 반려한다.** 반려할 때는 사유를 꼭 적는다.
  - AC: 승인되면 그 계정에 판매자 역할이 붙는다. 다음 토큰 갱신부터 판매자 앱에 들어갈 수 있다.
- **SEL-3 — 관리자는 판매자를 정지한다.** 정지되면 그 판매자의 상품이 모두 판매 중지되고 검색에서 빠진다.

### 3.3 상품·재고 (catalog, file)
- **CAT-1 — 판매자는 상품을 등록한다.** 카테고리, 이름, 설명, 이미지(최대 10장), 옵션 조합(SKU), SKU별 가격과 재고를 입력한다.
  - AC: 이미지를 올리면 썸네일이 생성된다. 상품에 붙지 않은 업로드 파일은 24시간 뒤 삭제된다.
- **CAT-2 — 판매자는 상품을 수정하고, 판매를 중지하거나 재개한다.** 변경 사항은 몇 초 안에 검색에 반영된다.
- **CAT-3 — 판매자는 SKU 재고를 조정한다.** 조정 이력이 남는다.
- **CAT-4 — 재고는 초과 판매되지 않는다.** 주문이 동시에 몰려도 판매 수량이 재고를 넘지 않는다.
- **CAT-5 — 관리자는 상품을 제재(판매 중지)한다.** 제재된 상품은 판매자가 직접 재개할 수 없다.

### 3.4 검색·탐색 (search)
- **SRC-1 — 구매자는 키워드로 상품을 검색한다.**
  - AC: 한국어 형태소 분석(nori)을 적용한다.
  - AC: 카테고리, 가격대, 별점으로 거르고, 관련도, 최신, 가격, 판매량, 별점 순으로 정렬한다.
- **SRC-2 — 구매자는 검색어 자동완성을 받는다.** (M5)
- **SRC-3 — 판매 중지 상품은 검색에서 빼고, 품절 상품은 뒤로 보낸다.**

### 3.5 장바구니·주문 (order)
- **ORD-1 — 구매자는 장바구니에 SKU를 담고, 수량을 바꾸고, 뺀다.** 장바구니는 판매자별로 묶어 보여준다.
- **ORD-2 — 구매자는 장바구니의 일부 또는 상품 하나를 바로 주문한다.**
  - AC: 주문 하나는 판매자별 하위 주문(`SellerOrder`)으로 나뉜다.
  - AC: 주문을 만들 때 가격과 판매 상태를 다시 확인한다. 가격이 바뀌었으면 주문을 만들지 않고 구매자에게 알린다.
  - AC: 재고와 쿠폰을 예약한 뒤 결제 대기 상태가 된다. 15분 안에 결제하지 않으면 주문이 만료되고 예약이 풀린다.
  - AC: 같은 주문 요청을 여러 번 보내도(새로고침, 재전송) 주문은 하나만 생긴다. 요청마다 멱등성 키를 쓴다.
- **ORD-3 — 구매자는 주문 목록과 상세를 본다.** 상세에는 판매자별 진행 상태가 나온다.
- **ORD-4 — 판매자는 자기 하위 주문만 보고 처리한다.**

### 3.6 결제 (payment)
- **PAY-1 — 구매자는 토스페이먼츠 결제위젯으로 결제한다.**
  - AC: 결제를 승인하기 전에 서버가 금액을 주문 금액과 대조한다. 다르면 승인하지 않는다.
  - AC: 승인 요청이 타임아웃되면 결제 조회로 실제 상태를 확인한 뒤 처리한다.
- **PAY-2 — 결제 후 주문이 취소되면 전액 또는 부분 환불한다.** 하위 주문 단위로 부분취소할 수 있다.
- **PAY-3 — 결제 승인과 주문 만료가 겹쳐도 돈만 빠져나가는 일이 없어야 한다.** 결제가 승인됐는데 주문이 이미 취소되었으면 결제를 자동으로 취소한다.
- **PAY-4 — 모든 결제·취소 요청과 응답은 원장에 남는다.**

### 3.7 배송·구매확정 (fulfillment)
- **FUL-1 — 판매자는 하위 주문을 발주 확인하고, 송장 번호를 입력해 발송 처리한다.**
- **FUL-2 — 배송 상태(발송, 배송 중, 배송 완료)를 기록한다.** 택배사 연동은 비용 때문에 하지 않는다. 판매자 입력과 배송 시뮬레이터로 대신한다.
- **FUL-3 — 구매자는 배송 완료 후 구매확정한다.** 배송 완료 후 7일이 지나면 자동으로 구매확정된다.

### 3.8 클레임 (fulfillment, payment)
- **CLM-1 — 구매자는 발송 전 하위 주문을 취소한다.** 취소는 바로 승인되고 환불된다.
- **CLM-2 — 구매자는 배송 완료 후 구매확정 전까지 반품이나 교환을 신청한다.** 사유와 사진을 첨부한다.
  - AC: 판매자가 회수 상품을 검수하고 승인하면, 반품은 환불하고 교환은 다시 발송한다.
  - AC: 판매자 귀책이 아니면 배송비를 뺀다.
  - AC: 반품을 승인할 때 판매자가 재입고 여부를 고른다.
- **CLM-3 — 판매자가 반품 신청을 거부하면 사유를 남긴다.** 구매자는 관리자 중재를 요청할 수 있다.

### 3.9 쿠폰 (promotion)
- **PRM-1 — 관리자는 쿠폰을 만든다.** 할인 방식(정액·정률), 최소 주문 금액, 최대 할인, 유효기간, 발급 수량을 정한다. 판매자는 자기 상품 전용 쿠폰을 만든다.
- **PRM-2 — 구매자는 쿠폰을 내려받는다.** 선착순 쿠폰은 동시 요청이 몰려도 수량을 넘겨 발급하지 않는다. 한 사람에게는 한 장만 발급한다.
- **PRM-3 — 구매자는 주문할 때 쿠폰을 적용한다.** 주문이 취소되면 유효기간이 남은 쿠폰은 복원된다.

### 3.10 리뷰 (review)
- **REV-1 — 구매자는 구매확정한 주문 상품마다 리뷰를 한 번 쓴다.** 별점, 본문, 사진을 넣는다.
- **REV-2 — 상품의 평균 별점과 리뷰 수를 상품 상세와 검색 결과에 보여준다.**
- **REV-3 — 판매자는 리뷰에 답글을 달고, 관리자는 부적절한 리뷰를 숨긴다.**

### 3.11 정산 (settlement)
- **STL-1 — 구매확정된 하위 주문은 정산 대상이 된다.** 정산 금액은 판매가에서 수수료(카테고리별 요율)와 판매자 쿠폰 부담분을 뺀 금액이다.
- **STL-2 — 정산은 주 단위 배치로 확정한다.** 판매자는 정산 예정 금액과 내역을 본다.
- **STL-3 — 관리자는 확정된 정산을 지급 처리한다.** 실제로 송금하지 않고 지급 완료로만 기록한다.
- **STL-4 — 배치는 다시 실행해도 결과가 같다.** (멱등)

### 3.12 알림 (notification)
- **NTF-1 — 가입 인증, 주문 완료, 발송, 클레임 결과, 정산 확정을 이메일과 인앱 알림으로 보낸다.** 이메일은 로컬 Mailpit으로 받는다.
- **NTF-2 — 같은 이벤트로 알림이 두 번 가지 않는다.**

### 3.13 관리자 운영 (admin 앱)
- **ADM-1** 입점 심사와 판매자 정지 (SEL-2, SEL-3)
- **ADM-2** 상품 제재(CAT-5), 리뷰 숨김(REV-3), 클레임 중재(CLM-3)
- **ADM-3** 쿠폰 관리(PRM-1), 정산 지급(STL-3)
- **ADM-4** 운영 지표: 일별 주문 수, 거래액(GMV), 결제 실패율. 관리자 작업은 모두 감사 로그로 남긴다.
- **ADM-5** DLT에 쌓인 메시지를 보고 다시 처리한다. (NFR-3)

## 4. 비기능 요구사항
"운영 가능한 수준"은 아래 항목으로 판단한다. 각 항목을 어느 마일스톤에서 검증하는지는 [roadmap.md](roadmap.md)에 적는다.

| ID | 항목 | 기준 |
|---|---|---|
| NFR-1 | 정합성 | 서비스 사이 상태 변경은 Outbox와 이벤트로만 전파한다. DB 커밋과 이벤트 발행은 원자적이어서 이벤트가 유실되지 않는다. 소비자는 멱등이다 |
| NFR-2 | 멱등 API | 주문 생성, 결제 승인, 쿠폰 발급, 클레임 신청 같은 상태 변경 API는 `Idempotency-Key` 헤더를 받는다. 같은 키로 다시 보내면 첫 응답을 그대로 돌려준다 |
| NFR-3 | 재시도·DLT | 일시 오류는 지수 백오프로 재시도한다. 끝까지 실패한 메시지는 DLT 토픽으로 보내고, 관리자가 다시 처리할 수 있다 |
| NFR-4 | 장애 격리 | 서비스 사이 동기 호출에는 타임아웃과 서킷 브레이커를 건다. 검색이 죽어도 주문과 결제는 동작한다 |
| NFR-5 | 레이트 리밋 | Gateway에서 사용자와 IP 단위로 요청을 제한한다. 로그인과 쿠폰 발급에는 더 엄격한 한도를 둔다 |
| NFR-6 | 보안 | 브라우저에 토큰을 노출하지 않는다(BFF). 각 서비스도 JWT를 검증한다. 비밀 값은 `.env`에만 두고 커밋하지 않는다. 마일스톤마다 OWASP Top 10을 점검한다 |
| NFR-7 | 개인정보 | 로그와 API 응답에서 이름, 전화번호, 주소, 계좌를 마스킹한다. 본인 정보를 본인에게 보여 주는 응답은 원문이다(2026-10-18 결정). 판매자는 배송에 필요한 구매자 정보만 본다 |
| NFR-8 | 감사 | 관리자 작업과 금액 변경(결제, 환불, 정산)은 누가, 언제, 무엇을 했는지 남긴다 |
| NFR-9 | 성능 | 로컬에서 k6로 측정한다. 상품 조회와 검색은 p95 200ms 이하, 주문 생성은 p95 500ms 이하(PG 호출 제외). 선착순 쿠폰 1,000건 동시 요청에서 초과 발급 0건 |
| NFR-10 | 관측성 | 요청 하나를 Gateway부터 Kafka 소비자까지 트레이스 하나로 따라갈 수 있다. 서비스마다 RED 지표(요청 수, 오류, 지연) 대시보드가 있다. 로그에 trace id가 찍힌다 |
| NFR-11 | 테스트 | 도메인은 단위 테스트, 저장소와 메시징은 Testcontainers 통합 테스트로 검증한다. 마일스톤마다 E2E 시나리오를 둔다 |
| NFR-12 | 재현성 | 새 PC에서 [dev-setup.md](dev-setup.md)대로 따라 하면 전체 스택이 뜬다. 스키마는 Flyway로만 바꾼다 |

## 5. 범위 밖
- 실제 송금, 실제 택배사 연동, 세금계산서 발행
- 클라우드 배포, 멀티 리전, 쿠버네티스
- 모바일 네이티브 앱 (웹은 반응형으로 만든다)
