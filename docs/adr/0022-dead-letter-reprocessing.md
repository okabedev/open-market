# 0022. DLT 메시지는 소비한 서비스가 자기 스키마에 모으고, 그 그룹만 받도록 원래 토픽으로 다시 보낸다
- 상태: 승인
- 날짜: 2026-10-26

## 맥락
관리자는 DLT에 쌓인 메시지를 보고 다시 처리해야 한다(ADM-5, NFR-3). 지금의 DLT 구조와 제약은 다음과 같다([messaging.md](../architecture/messaging.md) "소비: 멱등 소비자").
- DLT는 토픽마다 하나(`<토픽>.DLT`)다. 소비자 그룹 여럿이 같은 DLT를 쓴다. Spring Kafka가 헤더 `kafka_dlt-original-consumer-group`에 실패한 그룹을 적는다.
- 토픽 보관 기간은 7일이다. DLT만 읽어서는 7일 지난 메시지를 볼 수 없고, 다시 보냈는지도 남지 않는다.
- 원래 토픽으로 다시 보내면 그 토픽을 읽는 모든 그룹이 받는다. 이미 처리한 그룹은 `processed_event`로 거르지만, 이 기록은 30일 뒤 지워진다. 30일이 지난 이벤트를 다시 보내면 다른 그룹이 한 번 더 처리한다.
- 리스너는 `ConsumerRecord`를 받는 `@KafkaListener` 메서드다. 서비스 안에서 저장해 둔 메시지를 리스너에 바로 넣을 공개 API가 없다.
- 서비스는 다른 스키마를 읽지 않는다([ADR 0002](0002-single-postgres-schema-per-service.md)). 서비스 목록은 고정이다.

## 결정
- `common-messaging`이 서비스마다 DLT 수집기를 둔다. 수집기는 그 서비스의 리스너가 구독하는 토픽의 DLT를 별도 그룹(`<서비스>-dead-letter`)으로 읽는다. `kafka_dlt-original-consumer-group`이 자기 그룹인 메시지만 자기 스키마의 `dead_letter` 테이블에 넣는다. 키, 값, 원래 헤더, 예외 정보 헤더를 그대로 저장한다. `(DLT 토픽, 파티션, 오프셋)` 유니크로 같은 메시지를 두 번 넣지 않는다.
- 다시 처리할 때는 저장한 메시지를 원래 토픽의 원래 파티션으로 보낸다. 헤더 `dlt-target-group`에 대상 그룹을 적는다. `IdempotentEventProcessor`는 이 헤더가 있고 자기 그룹이 아니면 건너뛴다. 다른 그룹은 처리 기록 보관 기간과 상관없이 다시 처리하지 않는다.
- 다시 보낸 메시지가 또 실패하면 새 DLT 메시지가 되어 새 행으로 들어온다. 이벤트 ID로 앞의 행과 이어 본다.
- 행 상태는 `PENDING`(쌓임), `RETRIED`(다시 보냄), `DISCARDED`(관리자가 처리하지 않기로 함, 사유 필수)다. 다시 보내기와 버리기는 `PENDING`에서만 할 수 있다. 같은 요청을 다시 보내도 한 번만 보낸다(행 잠금 + 상태 검사). 두 작업은 감사 로그를 남긴다.
- 관리자 API는 서비스마다 `/v1/admin/dead-letters`(목록, 상세, 다시 보내기, 버리기)다. 화면은 admin BFF가 서비스들에 나눠 묻고 합친다([ADR 0023](0023-admin-ops-queries.md)).
- 응답에는 페이로드와 예외 메시지를 넣지 않는다. 개인정보가 들어갈 수 있다(NFR-7). 이벤트 `type`·`id`, 토픽 위치, 예외 클래스, 쌓인 시각, `traceparent`의 trace id를 준다. 원인은 trace id로 로그와 트레이스에서 찾는다.
- 자세한 규칙은 [messaging.md](../architecture/messaging.md) "DLT 재처리", 테이블은 [data.md](../architecture/data.md) "dead_letter"에 있다.

## 결과
- 좋아지는 점
  - 관리자가 7일이 지난 메시지도 보고, 누가 언제 다시 보냈거나 버렸는지 남는다.
  - 다시 보내도 실패한 그룹만 처리한다. 다른 그룹의 처리 기록이 지워졌어도 중복 처리가 없다.
  - 새 서비스, 새 토픽, 다른 스키마 읽기가 없다. 기존 리스너 코드는 바꾸지 않는다(멱등 처리기 한 곳만 바뀐다).
- 감수하는 점
  - 다시 보낸 메시지는 같은 키의 뒤 이벤트보다 늦게 온다. 그 사이 상태가 바뀌었으면 소비자가 상태 전이 규칙대로 무시한다(무시 지표로 센다). 순서가 중요한 실패는 런북에서 다룬다.
  - 서비스가 도메인 토픽에 직접 쓰는 경로가 하나 생긴다. 지금까지는 Debezium만 도메인 토픽에 썼다. 관리자 다시 보내기만 이 경로를 쓴다.
  - `IdempotentEventProcessor`를 거치지 않고 리스너 메서드에서 먼저 처리하는 코드가 있으면 대상 그룹 검사를 받지 못한다. 지금 리스너는 `type` 헤더로 분기만 하고 처리는 모두 처리기에 넘긴다. 테스트로 지킨다.
  - 수집기 소비자가 서비스마다 하나씩 늘어난다.
- 후속 작업: 두 그룹이 같은 토픽을 읽을 때 대상 그룹만 처리하는지 통합 테스트로 확인한다(R14).

## 검토한 대안
- **원래 토픽으로 대상 표시 없이 다시 보내기**: 가장 단순하지만, 처리 기록이 지워진 30일 뒤에는 다른 그룹이 다시 처리한다. 보관 기간 안의 이벤트만 다시 보내게 막는 방법도 있지만 오래된 실패를 처리할 수 없다.
- **서비스 안에서 저장한 메시지를 핸들러에 바로 넣기**: 다른 그룹에 닿지 않지만, 리스너마다 토픽·타입별 핸들러를 따로 등록해야 한다. 리스너 메서드를 그대로 쓰는 공개 API가 없다.
- **그룹별 재시도 토픽(`<토픽>.<그룹>.retry`)**: 대상이 분명하지만 토픽과 리스너가 그룹 수만큼 는다.
- **DLT 관리 전용 서비스**: 모든 DLT를 한 곳에서 보지만 서비스 목록에 없는 새 서비스가 필요하다.
