# 0017. 썸네일은 JDK ImageIO + TwelveMonkeys 리더로 서브샘플링해 만든다
- 상태: 승인
- 날짜: 2026-10-19

## 맥락
file.md는 상품 이미지를 올릴 때 썸네일(폭 300px, 800px)을 만들고, 라이브러리는 M2에서 정하기로 했다. 조건은 이렇다.
- 받는 형식은 JPEG, PNG, WebP다. JDK ImageIO는 WebP를 읽지 못하고, CMYK JPEG도 읽지 못한다.
- 서비스 컨테이너의 힙은 248MB다(R6, 512MB의 50%). 휴대폰 사진(4000x3000)을 그대로 풀면 48MB, 5천만 화소면 200MB다.
- 휴대폰 사진은 픽셀을 눕혀 저장하고 EXIF 방향으로 세운다. EXIF에는 촬영 위치(GPS)가 들어 있을 수 있다.
- 비용 0, 로컬 실행이다. 네이티브 바이너리를 이미지에 더하면 빌드와 유지보수 부담이 늘어난다.

## 결정
- 읽기는 JDK ImageIO에 TwelveMonkeys `imageio-jpeg`(CMYK·YCCK JPEG, EXIF 세그먼트), `imageio-webp`를 더한다. 쓰기는 JDK JPEG 기록기(품질 0.85)다. 버전은 ADR 0009 표에 있다.
- 처리 순서(`ImageIoImageProcessorAdapter`)
  1. 머리만 읽어 크기를 얻고, 픽셀 상한(5천만)을 넘으면 거절한다.
  2. 가장 큰 변형 폭의 2배 이상이 남는 정수 배율로 서브샘플링해 푼다(`ImageReadParam.setSourceSubsampling`). 6000px 원본은 2000px로 풀린다.
  3. 흰 배경 RGB로 옮기고, 절반씩 줄이다가 목표 크기로 맞춘다(쌍선형).
  4. JPEG EXIF 방향(1~8)대로 픽셀을 옮긴다. 줄인 뒤에 돌린다.
  5. 메타데이터 없이 JPEG으로 쓴다.
- 동시에 변형을 만드는 요청은 인스턴스마다 2개로 막는다(세마포어).
- 변형은 모두 JPEG이다. WebP로 쓰는 순수 Java 기록기가 없다.

## 결과
- 좋아지는 점
  - 테스트 픽스처(`services/infra/file/src/test/resources/images`, Pillow로 생성)로 확인했다: EXIF 방향 6인 120x80 사진이 80x120으로 서고 변형에 EXIF가 없다. CMYK JPEG, 투명 PNG(흰 배경), WebP를 읽는다. 1억 화소 PNG는 픽셀을 풀지 않고 크기만 읽어 거절한다. 잘린 JPEG은 `FILE_INVALID_IMAGE`다.
  - 서브샘플링 덕분에 원본 해상도와 상관없이 한 요청이 푸는 픽셀이 대략 1600px 폭 이미지 하나로 묶인다. 6000x4000 JPEG 10건 동시 업로드가 gateway 경유 0.8~2.9초에 끝났다.
  - 순수 Java라 실행 이미지에 네이티브 라이브러리를 더하지 않는다.
- 감수하는 점
  - 서브샘플링은 정수 배율로 픽셀을 건너뛰므로, 바로 줄이는 것보다 아주 가는 무늬에서 앨리어싱이 생길 수 있다. 2배 여유를 두고 다시 줄여 줄인다.
  - WebP·PNG의 방향 정보(EXIF·XMP)는 읽지 않는다. 휴대폰 사진은 거의 JPEG이다.
  - JPEG 결과라 WebP·AVIF보다 크다. CDN이 없으므로 긴 캐시로 보완한다.
  - 힙은 묶이지만 컨테이너 메모리는 다른 서비스보다 크다. 힙 밖(메타스페이스, 직접 버퍼, 디코더 네이티브 메모리)이 약 230MB라 공통 상한(512m, 힙 50%)에서는 스왑으로 밀렸다. file은 768m, 힙 40%, NIO 임시 직접 버퍼 캐시 끔으로 둔다. 실측은 risks.md R6 "메모리 예산".
- 후속 작업: 업로드가 많아 처리 시간이 문제가 되면 변형 생성을 비동기로 돌리는 방법을 M6 부하 테스트에서 검토한다.

## 검토한 대안
- **Thumbnailator**(0.4.21): 사용법이 간단하고 EXIF 방향을 처리하지만, 원본 해상도로 푼 뒤 줄인다. 5천만 화소 이미지는 힙 248MB를 넘는다. WebP는 결국 TwelveMonkeys가 필요하다.
- **libvips(외부 프로세스 또는 JNI 바인딩)**: 빠르고 메모리를 적게 쓰고 WebP·AVIF로 쓸 수 있다. 하지만 실행 이미지에 네이티브 라이브러리를 넣어야 하고, 서비스 공통 Dockerfile이 서비스마다 달라진다.
- **Scrimage**: WebP 쓰기를 위해 플랫폼별 `cwebp` 바이너리를 꺼내 실행한다. 컨테이너 안에서 바이너리를 실행하는 경로가 생긴다.
