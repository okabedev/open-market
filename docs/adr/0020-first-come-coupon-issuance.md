# 0020. 선착순 쿠폰은 Redis Lua 앞단 필터와 DB 조건부 발급·유니크로 지킨다
- 상태: 승인
- 날짜: 2026-10-23

## 맥락
PRM-2는 쿠폰을 선착순으로 내려받게 하고, 발급 수량을 넘기지 않고 회원마다 한 장만 주라고 한다. M5의 모든 쿠폰은 발급 수량이 있는 선착순 쿠폰이다([promotion.md](../architecture/promotion.md) "범위 결정").
- 인기 쿠폰은 발급이 열리는 순간 같은 쿠폰 행으로 요청이 몰린다. 요청마다 쿠폰 행을 잠그면 수량이 이미 끝난 뒤의 요청도 DB에서 줄을 선다.
- Redis 카운터와 회원 집합만으로 정하면 빠르지만, Redis 차지 뒤 DB 저장이 실패하거나 Redis가 재시작해 키를 잃으면 DB와 어긋난다. 어긋나면 수량을 넘겨 발급하거나 1인 2매가 된다(R11).
- Redis는 gateway 레이트 리밋과 BFF 세션에 이미 쓰고 있다. 새 인프라를 더하지 않는다(비용 0, 메모리 예산 R6).

## 결정
- 수량과 1인 1매의 마지막 방어선은 DB다.
  - 수량: 쿠폰 행 발급 수(`issued_count`)의 조건부 UPDATE(발급 중, 발급 기간 안, 발급 수 < 수량일 때만)와 `CHECK (issued_count BETWEEN 0 AND quantity)`.
  - 1인 1매: 발급 쿠폰 유니크 `(coupon_id, member_id)`와 `ON CONFLICT DO NOTHING`.
- Redis는 DB까지 가는 요청을 수량 근처로 줄이는 앞단 필터다. Lua 스크립트 하나로 회원 집합과 발급 수를 함께 확인하고 차지한다. 이미 받은 회원과 매진은 DB에 가지 않는다.
- DB 저장이 실패하면 Redis 차지를 되돌린다. DB가 매진이라고 하면 Redis 발급 수를 수량으로 올린다. Redis 키가 없으면 DB의 발급 회원으로 다시 채우는 것과 차지를 스크립트 하나로 한다.
- Redis를 부를 수 없으면 503 `PROMOTION_UNAVAILABLE`이다. DB만으로 발급하지 않는다.
- 다시 눌러도 같은 발급 쿠폰(200)을 주므로 `Idempotency-Key`를 받지 않는다.
- 규칙과 확인 결과는 [promotion.md](../architecture/promotion.md) "선착순 발급", "정합성"에 있다.

## 결과
- 좋아지는 점
  - Redis가 DB와 어긋나도 초과 발급이나 1인 2매가 되지 않는다. 수량 30에 회원 120명이 두 번씩 동시에 누르고 그사이 Redis 키를 20번 지워도 DB 발급 수 30, 회원당 1장이었다(`IssueCouponApiIntegrationTest`).
  - 매진 뒤와 이미 받은 회원의 요청은 Redis에서 끝나 DB 쿠폰 행에 줄을 서지 않는다.
  - 새 인프라 없이 쓰던 Redis와 Postgres로 끝난다.
- 감수하는 점
  - 차지한 요청이 되돌리기 전에 죽거나 되돌리기가 실패하면 Redis가 많게 센다. 그 쿠폰은 키가 사라질 때(발급 기간 끝 + 1시간)까지 수량보다 적게 나갈 수 있다. 초과 발급의 반대쪽이라 받아들인다.
  - Redis가 멈추면 발급이 멈춘다(503). 유스케이스 테스트(`IssueCouponUseCaseTest`)가 본다. 서비스를 모두 띄운 Redis 장애는 확인하지 않았다.
  - 키를 다시 만드는 동안 끼어든 요청을 따로 막지 않는다. Redis가 적게 세는 경우이고 DB가 막는다.

## 검토한 대안
- **DB만(쿠폰 행 잠금 또는 조건부 UPDATE)**: 정합성은 같지만 매진 뒤 요청과 이미 받은 회원의 요청도 모두 같은 행에서 줄을 선다. Redis 앞단이 그 요청을 DB 앞에서 끝낸다.
- **Redis만**: 가장 빠르지만 Redis와 DB가 어긋날 때 막을 곳이 없다. R11의 실패(초과 발급, 1인 2매)가 그대로 남는다.
- **분산 락(쿠폰마다 Redis 락)**: 요청을 하나씩 줄 세워 DB만 쓰는 것과 같은 병목이 생기고, 락 만료·소유 문제를 따로 다뤄야 한다.
- **발급 요청을 큐(Kafka)로 받아 순서대로 처리**: 순서는 분명하지만 구매자가 받았는지 바로 알 수 없다. 화면이 결과를 다시 물어야 하고, 발급 한 건마다 메시지 왕복이 더해진다.
