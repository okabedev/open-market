# 0021. 재고·쿠폰 예약 결과는 주문에 따로 기록하고 주문 행 잠금으로 합류한다
- 상태: 승인
- 날짜: 2026-10-23

## 맥락
M5에서 주문은 재고 예약(catalog)과 쿠폰 예약(promotion) 두 결과를 받아야 결제를 기다릴 수 있다([order.md](../architecture/order.md) "예약 결과"). 정합성은 코레오그래피 Saga로 맞춘다([ADR 0004](0004-choreography-saga.md)).
- 두 결과는 다른 토픽(`catalog.stock`, `promotion.issued-coupon`)으로 와서 순서를 정할 수 없다. 동시에 올 수도 있다.
- 한쪽이 실패할 수 있고, 같은 결과가 다시 올 수 있다(at-least-once).
- 어떤 경우에도 주문 상태가 하나로 정해지고, `OrderAwaitingPayment`나 `OrderCancelled`가 한 번만 나가야 한다. 받은 예약은 풀려야 한다(R12).

## 결정
- 성공 결과는 주문에 따로 기록한다(`stock_reserved`, `coupon_reserved`). 쿠폰이 없는 주문은 재고 결과 하나로 정한다.
- 결과를 처리할 때 주문 행을 잠근다(`SELECT ... FOR UPDATE`). 두 결과가 동시에 와도 하나씩 처리되고, 필요한 결과를 모두 받은 둘째 트랜잭션만 `PENDING` → `AWAITING_PAYMENT`로 바꾸고 `OrderAwaitingPayment`를 낸다.
- 실패가 오면 다른 쪽을 기다리지 않고 취소하고 `OrderCancelled`를 낸다. 그 뒤에 온 성공은 취소된 주문이라 넘긴다. 둘 다 실패하면 먼저 받은 실패의 사유가 남는다.
- 받은 예약은 catalog와 promotion이 `OrderCancelled`로 푼다. 리스너는 처리 기록(`processed_event`)으로 같은 이벤트를 한 번만 처리한다.
- 규칙은 [order.md](../architecture/order.md) "예약 결과"에 있다.

## 결과
- 좋아지는 점
  - 결과가 어떤 순서로 와도, 한쪽이 실패해도, 다시 와도 상태가 하나로 정해진다. 순서·중복·실패 조합(Kafka)과 두 리스너를 같은 주문에 동시에 돌리기(두 스레드 × 20회)에서 주문 이벤트가 한 번만 나갔다(`ReservationJoinIntegrationTest`). M5 E2E에서 재고·쿠폰 예약이 함께 성공한 주문이 결제되고 쿠폰이 사용됨이 됐다.
  - 새 서비스(조정자)나 새 토픽 없이 order 안에서 끝난다. 실패 쪽은 기존 `OrderCancelled` 보상을 그대로 쓴다.
  - 예약이 하나 더 생겨도 같은 방법(결과 기록 칸 하나)으로 늘릴 수 있다.
- 감수하는 점
  - 같은 주문의 결과 처리는 잠금으로 줄을 선다. 주문마다 결과가 둘이라 대기는 짧다.
  - 실패가 먼저 오면 다른 쪽 성공을 기다리지 않아, 잠깐 받아 둔 예약을 보상으로 푸는 일이 생긴다.
  - 실패 조합을 서비스를 모두 띄운 E2E로는 보지 않았다(통합 테스트가 본다).

## 검토한 대안
- **조정자(오케스트레이션)**: 주문 Saga를 한 곳에서 이끌면 순서가 분명하지만, ADR 0004의 코레오그래피와 다르고 새 구성 요소와 상태 저장이 필요하다.
- **예약을 차례로(재고 → 쿠폰)**: 순서가 하나라 합류가 필요 없지만 주문 시간이 두 단계로 길어지고, catalog가 promotion 결과를 기다리는 연결이 생긴다.
- **잠금 없이 낙관적 버전 검사**: 동시에 온 두 결과 중 하나가 버전 충돌로 재시도된다. 결과는 같지만 재시도가 리스너 오류 처리(재시도·DLT)로 흘러가 원인을 보기 어렵다. 주문 행 잠금이 더 단순하다.
