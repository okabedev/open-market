# 0007. DDD + CQRS 패키지 구조
- 상태: 승인
- 날짜: 2026-10-16

## 맥락
주문, 재고, 결제, 클레임은 상태 전이 규칙이 복잡하다. 반면 화면은 여러 집계를 합친 조회가 많다. 하나의 모델로 둘 다 하면 엔티티가 조회 요구로 오염된다.

## 결정
- 쓰기는 DDD 집계로 모델링하고, 읽기는 QueryDSL 프로젝션으로 View를 바로 만든다.
- 패키지는 `command/{application,domain}`, `query/{application,dao,dto}`, `infra`, `ui`로 나눈다.
- 의존 방향과 이름 규칙은 ArchUnit으로 빌드 때 강제한다([conventions.md](../architecture/conventions.md)).
- 실용적 타협: 도메인 엔티티에 Jakarta Persistence 애노테이션을 허용한다. 별도 영속 모델을 두지 않는다.
- 쿼리 쪽은 같은 DB 테이블을 읽는다. 읽기 전용 DB나 이벤트 소싱은 쓰지 않는다.

## 결과
- 좋아지는 점: 도메인 규칙이 한곳에 모인다. 조회 성능을 엔티티와 무관하게 튜닝할 수 있다.
- 감수하는 점: 조회 쪽에 enum과 타입을 따로 둬야 한다. 그래서 동기화 테스트가 필요하다.

## 검토한 대안
- 레이어드(Controller/Service/Repository): 익숙하지만 도메인 규칙이 서비스 클래스에 흩어진다.
- 헥사고날 + 별도 영속 모델: 경계는 깨끗하지만 매핑 코드가 크게 늘어난다.
