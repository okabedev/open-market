# 0019. 인앱 알림은 조회 방식으로 하고, 관리자 알림은 역할에 한 건만 둔다
- 상태: 승인
- 날짜: 2026-10-22

## 맥락
NTF-1은 주문 완료, 발송, 클레임 결과 같은 알림을 이메일과 인앱 알림으로 보내라고 한다. M4에서 세 앱(shop, seller, admin)이 각자 받는 쪽의 알림을 보여야 한다.
- 브라우저는 gateway를 직접 부르지 않고 토큰도 갖지 않는다([ADR 0006](0006-nextjs-bff.md), [ADR 0014](0014-bff-session.md)). 실시간 푸시를 하려면 BFF가 연결을 붙잡고 있어야 한다.
- 알림은 판매자의 새 주문·클레임, 구매자의 발송·클레임 결과, 관리자의 중재 요청·환불 실패다. 몇 초 안에 봐야 하는 것은 없다. 처리는 각 화면(주문, 중재, 결제 실패)에서 한다.
- notification은 관리자 명단을 모른다. 관리자는 auth의 역할이고, 관리자가 늘거나 줄어도 notification이 알 방법이 없다.
- 실행 환경은 로컬 Compose 하나이고 비용 0이다. 메모리 예산(R6)이 빠듯하다.

## 결정
- 조회 방식(polling)으로 한다. 서버 푸시(SSE, WebSocket)는 하지 않는다.
  - notification은 받는 쪽마다 목록(커서), 안 읽은 수, 읽음, 모두 읽음 API를 준다([notification.md](../architecture/notification.md) "인앱 알림").
  - 앱 머리글이 안 읽은 수를 보인다. 페이지를 열 때 서버(레이아웃)가 읽고, 클라이언트 이동으로 경로가 바뀔 때와 머무는 동안 60초마다 BFF Route Handler로 다시 읽는다. notification에 닿지 못하면 0으로 본다.
- 받는 쪽(`audience`)은 앱과 같다(`BUYER`, `SELLER`, `ADMIN`). 같은 회원이 구매자이자 판매자여도 앱마다 자기 알림만 보인다.
- 관리자 알림은 받는 사람 없이 `ADMIN` 역할에 한 건만 저장한다. 관리자라면 누구나 같은 목록을 보고, 읽음은 관리자마다 따로(`notification_read`) 둔다.
- 알림 문구와 이동 대상(`targetType`, `targetId`)은 알림을 만들 때 정해 저장한다. 앱은 문구를 그대로 보이고 이동 대상을 자기 화면으로 바꾼다.

## 결과
- 좋아지는 점
  - BFF가 오래 붙잡는 연결이 없다. 기존 세션·토큰 갱신 흐름(ADR 0014)과 gateway 레이트 리밋을 그대로 쓴다.
  - notification이 관리자 명단을 몰라도 된다. 나중에 생긴 관리자도 지난 알림을 보고, 관리자 수만큼 행이 늘지 않는다.
  - 알림 문구가 저장돼 있어 이벤트 형식이나 문구 규칙이 바뀌어도 지난 알림이 그대로 보인다.
- 감수하는 점
  - 머무는 화면에서는 새 알림이 최대 60초 늦게 보인다. 사용자 수만큼 60초마다 요청이 생긴다(로컬 규모에서는 문제없다).
  - 관리자 알림의 "누가 처리했는지"는 알림이 아니라 처리 화면(중재 목록, 결제 실패 목록)과 감사 로그로 본다.
  - 알림 문구를 바꾸면 이미 만든 알림에는 반영되지 않는다.
- 후속 작업: 실시간성이 필요한 알림(예: 채팅, 실시간 재고)이 생기면 SSE를 다시 검토한다.

## 검토한 대안
- **SSE(서버 전송 이벤트)**: 새 알림이 바로 보인다. 하지만 BFF가 사용자마다 연결을 붙잡고 Redis pub/sub 같은 전달 경로가 더 필요하다. 세션 만료·토큰 갱신을 스트림 안에서 다시 처리해야 하고, 지금 알림에는 그만한 실시간성이 필요 없다.
- **WebSocket**: SSE와 같은 부담에 양방향 프로토콜까지 더해진다. 보낼 쪽이 서버뿐이라 필요 없다.
- **관리자마다 알림 한 건씩**: 관리자별 읽음은 자연스럽지만 notification이 auth의 관리자 명단을 알아야 한다. 동기 조회나 별도 이벤트가 필요하고, 알림을 만든 뒤 생긴 관리자는 지난 알림을 못 본다.
